# 分支维护与研发流程

## 目的与范围

本文件规定 `magic-code` 的分支、验证、合并与发布方式，使每次变更可追溯、可复现、可验收。适用于本仓库的代码、测试、配置与构建脚本变更。测试方法与测试分层见 `TESTING.md`。

分支状态以 `git branch`、`git log` 为准；本文件只维护规则，不记录当前状态。

## 职责

- 需求负责人：确定范围、验收标准与优先级。
- 开发执行者：实现、验证并交付变更，维护分支与提交规范。
- 项目负责人：批准合入 `main`、发布与对外推送。

## 研发流程

| 阶段 | 产出 | 完成标准 |
| --- | --- | --- |
| 立项 | 需求／缺陷条目 | 范围、验收标准、基线明确 |
| 开工 | 短分支 | 从 `main` 切出；登记共享修改面与必跑门禁 |
| 实现 | 代码与测试 | 单一事实来源；行为变更同步测试；协议／接口变更同步文档 |
| 验证 | 检查记录 | 按门禁矩阵执行；交付说明列出 commit、检查结果、未验边界 |
| 核收 | 核收结论 | 对照验收标准检查实现与证据；确认最终提交 |
| 合并 | 合并提交 | 先合 `develop` 验证，通过后合 `main`；合并后重跑门禁 |
| 发布 | tag 与构建产物 | 从 `main` 打 tag；完成安装版／真机验收 |
| 收尾 | 台账更新 | 更新缺陷／台账状态；删除已合分支与工作树 |

## 分支模型

| 分支 | 角色 | 流向 |
| --- | --- | --- |
| `main` | 核心分支与唯一发布基线 | 接收 `develop` 验证通过的变更；发布 tag 打在 `main` |
| `develop` | 最新开发验证分支 | 接收短分支提交；验证通过后合入 `main`；`main` 更新后同步 |
| `0.1.0` | 过渡分支：处理 0.2.0 时切出的原始分支 | 0.1.x 修复回灌 `main`／`develop` 后对齐；不长期双线维护 |
| `0.2.0-migration` | 0.2.0 重构长期分支 | 完成后先合 `develop` 验证，再合 `main` |
| `feat/*`、`fix/*`、`u*` | 短工作分支 | 从 `main` 切出；合入 `develop`；合并后删除 |
| `release/*`、`hotfix/*` | 发布稳定化与线上修复 | 发布需要时建立；合回 `develop`／`main`；tag 在 `main` |

分支命名：`feat/<scope>`、`fix/<scope>`、`release/<version>`、`hotfix/<version>`。

短分支从 `main` 切出，合入 `develop` 前同步 `develop` 的最新提交。`develop` 验证通过后合入 `main`；`main` 出现新提交后同步回 `develop`。已合入目标分支的短分支在合并后删除。

## 版本与发布

- 版本号：`package.json` 与 `packages/contracts/src/native.ts` 的 `SOFTWARE_VERSION` 同版；`scripts/macos/build.sh` 负责校验。
- 发布：`develop` 验证通过并合入 `main`；`main` 通过 `bun run check` 与 `bun run check:macos`；从 `main` 打 annotated tag `v<version>`；推送 `main`、`develop` 与 tag。
- 发布后修复：从 `main` 切 `hotfix/*`，合 `develop` 验证、合 `main`，重打 patch tag。
- 同一时间只维护一个发布基线；`0.1.0` 是过渡分支，不建立长期 0.1.x 版本线。

## 质量门禁

| 改动面 | 合入 `develop` | 合入 `main`／发布 |
| --- | --- | --- |
| 纯文档 | 内容、链接、差异 | 同上 |
| 纯逻辑／单包 | `bun run test:fast` | `bun run check` |
| 跨包、协议、设置消费、持久化 | `bun run check` | `bun run check` |
| CLI／Engine／PTY 用户流程 | `bun run check` + 对应 e2e | `bun run check` + 匹配的 macOS 门 |
| Swift／AppKit／原生协议／打包 | 相关 NativeTests | `bun run check:macos` |
| 发布 | — | `bun run check:all` + 安装版／真机验收 |

- pre-commit 的 `check:commit` 是提交门；合并门按上表执行。
- CI 在 PR 与手动触发时运行；直接合并 `main` 时由本地完成对应检查。
- 门禁失败时定位原因并修复后重跑；测试用例的增删按 `TESTING.md` 的维护规则执行。

## 合并规则

- 合并条件：目标分支最新、工作区干净、最终提交已核、门禁通过。
- `develop` → `main` 优先 `--ff-only`；需要 merge 时记录原因。
- `0.2.0-migration` 用显式 merge，保留重构历史。
- 冲突解决后重跑匹配门禁，并检查测试、文档与代码的一致性。
- 合并后以目标分支的实际行为验收。

## 提交规范

- 一个提交只做一件事；信息格式 `<类型>(<范围>): <结果>`，类型用 `feat`、`fix`、`refactor`、`test`、`docs`、`chore`、`merge`。
- 提交前运行 `git diff --check`；提交内容包含本次变更所需的代码与测试。
- 已推送历史不改写；回滚使用 `revert`。

## 产品透明与可观测

- 界面显示与请求解析使用同一来源；兜底值在界面标出来源。
- 保存与选择阶段允许先配置后校正；请求前对明确不支持的能力说明具体原因。
- 默认值、兜底与失败信息对用户可见。
- 官方支持提示表只记录已核实的事实；未核实的能力按兜底处理并显示来源。
- 交付时一次性列出已验证范围与未验证范围。

## 规则维护

- 测试细则在 `TESTING.md`；本文件维护分支、发布、合并与提交规则。
- 规则变更由项目负责人批准，并在版本库中记录。
- 新增分支类型、版本线或发布方式时，先更新本规则再执行。
